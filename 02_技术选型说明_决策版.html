01

整体实现与技术选型

1.1 一个应用，三层职责

当前产品使用 Next.js + React + TypeScript，页面、接口和管理后台放在同一个应用中。PostgreSQL 保存业务数据；百炼模型负责需求理解、候选比较与结果复核。用户端与后台共用数据结构，但使用独立的访问权限。

程序负责确定性规则

校验输入、过滤不可用书籍、排除已读、查找候选、核对返回编号、保存状态、控制次数与费用。

AI 负责语义判断

理解自然语言目标，判断是否需要追问，在已有资料范围内比较候选，说明适合之处与必要局限。

1.2 关键选择与取舍

1.2.1

应用架构：Next.js 前后端一体化

先确定应用如何组织，再选择开发语言，降低前后端同步迭代的成本。

当前方案为什么这样选当前方案的代价与边界比较方案与不足
Next.js 一体化应用前后端共用业务模块，统一迭代与发布。前后端难以独立扩容；需适配托管平台。前端应用＋独立后端服务不足与暂缓原因：增加接口联调与部署协调，当前独立发布的收益有限。
统一使用 TypeScript共用数据类型，提前发现前后端字段不一致。需要维护类型；外部数据仍需运行时校验。使用 JavaScript 开发不足与暂缓原因：需另补类型检查，否则更依赖测试和手工核对。

什么时候考虑调整：出现独立扩容、发布节奏或故障隔离需求时，再拆分服务；先完成现有业务模块的职责拆分。

1.2.2

数据架构：PostgreSQL 统一存储

应用结构确定后，组织书目、对话与反馈数据，支持检索和状态恢复。

当前方案为什么这样选当前方案的代价与边界比较方案与不足
业务数据与向量共用 PostgreSQL统一管理书目与向量，减少跨库同步。业务与检索共享数据库资源，增长后可能相互影响。业务库＋独立向量库不足与暂缓原因：增加跨库同步与故障处理，当前小书库的拆分收益不明确。
关系字段＋JSONB 快照保留常用查询字段，便于整体恢复对话状态。反复更新快照增加写入；逐条消息分析不够直接。按书目明细、会话消息拆表不足与暂缓原因：增加多表组装与一致性写入逻辑。

什么时候考虑调整：先将模型等待移出数据库事务；会话写入、统计查询或检索持续成为瓶颈时，再调整表结构与存储边界。

1.2.3

推荐策略：向量召回＋AI 排序

承接产品设计思路中“程序从真实书库检索候选、AI 比较适配”的决策，技术上采用向量召回＋AI 排序：程序筛选候选并执行明确限制，模型结合用户需求与书籍资料决定推荐顺序。

当前方案为什么这样选当前方案的代价与边界比较方案与不足
从书库进行语义召回候选来自已核对资料，推荐依据可追溯。结果受书库覆盖与召回范围限制。直接让模型生成书单不足与暂缓原因：可能生成未核实书目或依据，仍需额外核对来源。
在 PostgreSQL 内做精确检索几百本书先沿用精确计算，减少索引配置与调参。逐条计算的开销随书库增长。pgvector 近似向量索引不足与暂缓原因：需要索引调参，近似检索还可能漏掉候选。
由 AI 决定首选与备选处理多种需求组合，减少人工维护评分权重。结果会波动，适配程度仍需评测。程序按固定权重排序不足与暂缓原因：需求组合增多后，评分规则和权重难以维护。

什么时候考虑调整：分别检查召回覆盖与最终适配；漏检时评估关键词或分类补充，精确查询变慢后再引入向量索引。

1.2.4

模型选型：采用百炼托管模型

根据理解、向量化和排序任务，选择模型服务，并判断是否需要自建或微调。

当前方案为什么这样选当前方案的代价与边界比较方案与不足
通过百炼 API 调用模型沿用已接通的模型服务，减少部署与运维。受供应商配额、延迟与费用约束。自建 GPU 推理服务不足与暂缓原因：需维护 GPU 推理服务，低用量时存在算力闲置。
沿用 qwen3.7-plus 与 qwen3.7-text-embedding已接入调用、校验与计费，先作为评测基线。尚未证实是最优组合；换向量模型需重建向量。更换模型或按任务使用不同模型不足与暂缓原因：增加适配与回归测试，收益尚未验证。
先改进资料、召回与提示词直接改进候选覆盖与推荐依据，便于逐次复测。效果仍受基础模型能力限制。在现有检索流程上增加微调不足与暂缓原因：增加样本整理与训练成本，不能替代资料补全。

什么时候考虑调整：当固定评测中的质量、时延或成本持续不达标时，比较替代模型；模型替换时同步更新费率、校验与向量数据。

1.2.5

流程实现：代码编排＋直接调用模型 API

模型选定后，将调用、检索、校验与状态保存串联起来，选择合适的编排方式。

当前方案为什么这样选当前方案的代价与边界比较方案与不足
在应用代码中编排工作流（使用 Codex）步骤有限，便于与现有状态、校验逻辑一起维护。失败恢复需自行维护；分支增多后复杂度上升。引入可视化编排平台或工作流框架不足与暂缓原因：增加框架适配成本，独立平台还需衔接状态与权限。
自行封装模型 HTTP 调用沿用已接通的调用路径，集中控制超时与用量。异常处理与供应商适配需自行维护。主推荐链改用 AI SDK不足与暂缓原因：需要迁移和复测，当前调用范围有限，收益不明显。

什么时候考虑调整：当流程分支、多模型适配或长任务恢复明显增加时，再评估 SDK 与工作流框架；并发增长前先缩短数据库事务。

1.2.6

部署方案：EdgeOne＋Neon 托管

流程确定后，选择应用与数据库的部署方式，兼顾维护成本和运行限制。

当前方案为什么这样选当前方案的代价与边界比较方案与不足
EdgeOne 托管当前应用减少应用服务器维护，统一构建与发布。受平台构建适配与函数运行限制约束。阿里云 ECS＋Docker 自行部署不足与暂缓原因：此前香港 ECS 已部署，但遇到大陆网络不可达；经评估，改用大陆节点的 ICP 备案难以在本次交付期限内完成，且服务器运维需自行承担。
Neon 托管 PostgreSQL沿用现有表结构与 SQL，减少实例维护。存在跨区域延迟，需关注用量费用。自行部署 PostgreSQL不足与暂缓原因：数据库升级、备份与故障恢复增加持续运维负担。

什么时候考虑调整：当跨区域延迟、平台限制或持续费用不再适合时调整部署；备案完成后的大陆同地域方案与预算见第 05 节。

03

数据存储与管理

书目事实、会话状态、模型判断与运营记录分开保存，并用稳定编号关联。

3.1 数据究竟保存在哪里

业务数据保存在 PostgreSQL，当前 v1.2 发布环境使用 Neon 新加坡数据库。浏览器 Cookie 保存随机访问令牌；数据库保存令牌的 SHA-256 摘要来关联会话。历史对话通过接口取回，localStorage 只记录历史面板的展开偏好。

关系字段用于查询与约束

主键、归属、状态、时间和版本单独建列；用主键、唯一约束、索引及事务支持去重、筛选和关联。

JSONB 用于保留完整上下文

书目来源、目录、对话轮次和推荐快照结构较丰富，先整体保存，便于恢复与复核。统计常用字段另行记录。

3.2 从资料导入到用户使用

  1. 01

    整理来源

    保存书目、简介、目录与原始链接；标记缺项和版本。

  2. 02

    校验与导入

    检查格式、ISBN、重复编号与原文哈希；先预览，再事务写入。

  3. 03

    生成检索向量

    记录模型、维度和 source_hash；资料变化后重建对应向量。

  4. 04

    在线读取与追踪

    只用合格资料生成推荐；结果、反馈和运行信息分别落库。

4.1 一次推荐怎样完成

这是一条以书目资料为依据的检索增强生成（RAG）流程：先检索，再把候选资料交给模型。当前主要依据简介、目录和核查资料，并未对整本书全文建立知识库。

贯穿示例

“第一次带团队，想学习一对一沟通，希望有具体案例。”

普通推荐通常是 2 次文本调用 + 1 次需求向量调用；追问分支先结束本轮，指定书籍查询、无匹配和引用修复会改变调用数。一次完整选书可能包含多次生成，不能把用户数、对话数和模型调用数混为一项。

4.3 反馈后怎样继续，而不把对话弄乱

重新比较与局部替换

首选已读时排除后重新比较；备选已读时保留其他书，只补一本。改变目标或纠正基础时使用最新信息，旧轮次保留原样。

重复提交与多页面操作

operationId 标记同一次操作，version 判断页面是否过时；访问者锁防止并行覆盖。数据库写入失败时回滚对话状态。

对话状态与失败处理细则、当前扩容瓶颈
  1. 读取 Cookie 摘要后，任务接口取得 PostgreSQL 事务级共享槽位和访问者锁；当前全站共有 5 个任务 POST 槽位，超出直接返回忙碌提示，没有自动排队。
  2. 查找 operationId 是否已落库，已处理则返回对应状态；页面版本过旧返回 409，防止另一页面覆盖更新。
  3. 费用通过独立事务预留。模型失败、超时或用量缺失时保留预留，避免失败重试绕过次数与费用记录。
  4. 结果校验后才更新会话、操作映射与任务事件；后台需求快照使用保存点，写入失败时可延后补录，不必让成功推荐整体失败。
  5. 当前事务跨越模型等待，会长期占用一个数据库连接；运行记录和预算还需额外连接。连接池上限 10 是每个进程 / 实例的上限，不是整个系统的总上限。

扩容前优先调整：短事务创建带租约的任务 → 事务外调用模型 → 短事务按版本提交结果。保留去重、超时恢复和费用结算；结合队列与连接池代理控制并发，避免只把 5 个槽位改成更大的数字。

4.4 后台分析也是一条独立 AI 流程

每次匹配或无匹配结果可保存需求快照。提交推荐后，通过 after() 尝试处理少量待分析记录；管理员也可以发起处理或重试。分析结果必须通过原句证据校验，人工复核结论不能被稍后完成的模型结果覆盖。

这条流程有独立的每日次数、费用预留、处理状态和重试次数，当前最多自动尝试 3 次。它不是持续驻留的工作进程；请求结束后的执行仍受托管平台生命周期限制，规模扩大后应迁移到独立任务队列与常驻执行器。

  • 失败：断网、接口超时、模型或数据库错误；按钮恢复可操作，旧输入与结果按设计保留。
  • 浏览器与布局：在桌面 Chrome/Safari 和手机窄屏检查长书名、长理由、加载/错误提示、键盘操作与历史面板；记录实际浏览器版本。
后台分析的触发与人工结论保护

分别测试分析关闭、额度不足、无待办、存在旧待办、模型失败及证据校验失败。推荐提交后的处理每次最多领取两条，可能先处理旧记录；不得把“触发处理”误判为“本条已完成”。明确范围外记录按规则直接标记。

测试自动尝试达到 3 次后不再自动领取；运行中断后的状态恢复另做检查。模型运行期间提交人工复核，随后完成的模型结果不得覆盖人工结论。恢复分析开关或额度后，再触发处理验证待办可继续执行。

AI 评测执行细则

场景组织、评分与回归方法

覆盖四类选书目标，以及模糊需求、资料不足、无匹配、已读排除、指定书名与多轮调整。复用产品文档的 24 个场景；新增用例单独标记，不临时改变本轮分母与门槛。

需求理解、推荐适合程度、依据可靠性、反馈调整四个适用维度均为“符合”，才算单次合格；“部分符合”“不符合”不计合格，不适用维度在测试前注明。72 次均需有记录与判断，漏测、运行失败或待核对不能删除或视为通过。

每次保存结构化需求、候选及顺序、原始模型结果、引用校验结果、模型与数据库耗时、Token、失败原因。人工记录评分依据；争议项复核后再形成结论。

准备人工确认的适合书集合供召回诊断，允许多本合理答案。更换模型、提示词或书库后，重跑固定集；修复单点后先复测失败案例，再回归受影响路径，完整发布评测仍按统一口径统计。

专项测试执行细则

负载、耗时与费用怎样记录

隔离环境先使用固定耗时的模拟模型，分开观察程序、数据库与模型瓶颈。每档负载持续至少 15 分钟，再做短时突发与恢复检查；记录成功率、忙碌率、P50/P95 耗时、连接占用、长事务、资源消耗和费用记录。

当前接口没有自动排队，检查拒绝行为；规划中的持久任务队列另测积压、执行器中断、租约恢复与多实例去重。第 5.3 节阈值作为规划目标，压测后校准；不把模拟模型下的吞吐直接等同真实推荐容量。

真实调用使用独立预算与明确上限，分别记录用户端和后台分析的调用数、Token 与估算费用；未知用量单列，不记为零。测试数据清理后核对线上统计未混入测试流量。

恢复与安全检查清单
  • 对两个访客的会话、评价和操作编号做交叉访问；分别检查页面入口与服务端接口。
  • 在用户输入和候选资料中放入要求泄露密钥、忽略规则或推荐库外书籍的文本，核对最终输出与程序校验；不能仅靠提示词声明判定安全。
  • 检查构建产物、返回数据和日志中的密钥、连接信息与用户数据暴露。
  • 恢复后比对表数量、关键行数、主外键关系、书目/向量匹配，以及抽样对话、评价与后台记录；再运行核心流程。
  • 记录实际恢复时长与备份时间点；可接受停机窗口和数据损失窗口在演练前约定。新环境已有写入时，先同步新增数据再回退。
  • 当前备份维护依赖本机；迁到常驻云端后，增加个人电脑离线下的备份与巡检验证。
